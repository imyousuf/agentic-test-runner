# Compiled Behavior Tests

A behavior test is written in English. Running it used to mean handing the
spec to an agent and letting it work out every step, every time — which is
accurate but costs a model call per action on every run.

ATR now compiles the spec to JavaScript once and replays that script on
subsequent runs. The script is the *shadow* of the agent run: the same
sequence of actions, minus the model. The agent comes back only when the
script fails, to work out why.

```bash
atr run --behavior tests/shop.test.txt      # compiles on first run, replays after
```

Concretely, for a six-step spec:

| Run | What happens | Model calls | Time |
| --- | --- | --- | --- |
| First | Agent drives the browser, then emits `shop.test.js` | many | minutes |
| Every run after | The script replays | **0** | **164 ms** |
| App genuinely breaks | Script fails on an assertion | **0** | 0.6 s |
| UI is refactored | Agent repairs the script, re-runs | 1 | seconds |

## The compiled script

`shop.test.txt` compiles to `shop.test.js` next to it. It is meant to be
committed: it is the thing that actually runs, so it should be reviewable in a
diff and reproducible on a machine that has never run the compiler.

```javascript
// Generated by ATR from shop.test.txt — edit the spec, not this file.
// atr-spec-sha256: d92c63ce682a74d7...

atr.step(1, "Verify the page heading says \"Demo Shop\"", () => {
  atr.navigate("");
  atr.waitFor("#title");
  expect(atr.text("#title")).toBe("Demo Shop");
});

atr.step(2, "Add the Widget to the cart", () => {
  atr.click("[data-testid=\"add-widget\"]");
});
```

The header records a hash of the spec. Edit the spec and the next run
recompiles; reflow the whitespace and it does not, because a reformat should
not cost tokens.

Scripts run in an embedded JavaScript interpreter (goja) inside ATR — there is
no Node, no `npm install`, and ATR remains a single binary. There is also no
DOM and no network: a script can only reach the browser through the `atr`
library below.

## Why it fails matters more than that it failed

A compiled test only pays for itself if a failure can be triaged without a
human. Three things can go wrong, and they have opposite correct responses:

| Kind | Means | Response |
| --- | --- | --- |
| `assertion` | The application is wrong | **Report it.** Never repaired. |
| `not_found` | An element moved or was renamed | Agent repairs the script |
| `timeout` | Something was slow | Retry, then ask the agent |
| `environment` | Browser/network/daemon problem | Retry, report as infra |
| `script` | The generated code is wrong | Agent repairs the script |

The distinction that matters most is **assertion vs not_found**. A suite that
repairs itself until it passes is a suite that launders regressions. So:

- **An assertion failure never reaches the model.** The runtime already knows
  the application is wrong. Asking a model to confirm it would spend the
  tokens this design exists to save, and invites it to "fix" the assertion
  that caught the bug.
- **A repair must justify itself.** Before rewriting, the agent has to say
  what the application still does that satisfies the spec. If the behaviour
  the spec asks for is gone, that is a test failure however much the page
  changed around it.
- **Assertions are never weakened.** Repair rewrites how the script reaches
  the application, not what it demands of it.

This is why the generated code style matters. `atr.click("#buy")` failing
means drift, so a script must never use a bare click to assert that a button
exists — it writes `expect(atr.exists("#buy")).toBeTruthy()` instead, or a
real regression would be quietly repaired away.

## The script API

Everything a script can do. There is no DOM, no `require`, no `fetch`.

**Structure**

```javascript
atr.step(n, "description", () => { ... })   // one per spec step
atr.log(msg)  atr.fail(msg)  atr.sleep(ms)  atr.retry(times, fn)
atr.base                                    // the base URL
```

**Navigation** — `atr.navigate(url)` (relative URLs resolve against
`atr.base`), `atr.reload()`, `atr.back()`, `atr.forward()`

**Interaction** — `atr.click`, `atr.doubleClick`, `atr.fill(target, value)`,
`atr.fillSecret(target, {ref})`, `atr.hover`, `atr.pressKey`, `atr.scroll`

**Waiting** — `atr.waitFor(target, {timeout, visible})`,
`atr.waitForText(text, {timeout})`

**Reading** — `atr.exists(target)` (returns a boolean, never throws),
`atr.text`, `atr.html`, `atr.url`, `atr.title`, `atr.snapshot`, `atr.eval`,
`atr.consoleErrors`, `atr.failedRequests`

**Pages** — `atr.newPage`, `atr.listPages`, `atr.selectPage`, `atr.closePage`

**Assertions** — `expect(v).toBe/.toEqual/.toContain/.toMatch/.toBeTruthy/`
`.toBeFalsy/.toBeGreaterThan/.toBeLessThan/.toHaveLength`

Three calls look similar and are not:

- `expect(...)` and `atr.fail()` say **the application is wrong**. Reported,
  never repaired.
- A missing target in `click`/`fill` says **the page changed shape**. Repair
  candidate.
- `atr.waitFor` says **not yet**. Retried before anything else.

`atr.retry` only re-runs *transient* failures, so wrapping an `expect()` in it
achieves nothing — wait for the state first, then assert once.

## Flags

| Flag | Effect |
| --- | --- |
| *(none)* | Compile if needed, replay, repair on drift |
| `--recompile` | Regenerate the script even if it matches the spec |
| `--no-compile` | Replay only, never call the model. Fails if a script is missing or stale |
| `--no-repair` | Diagnose drift but leave the script alone |
| `--interpret` | Skip compilation; the agent drives every step, as before |

**Use `--no-compile` in CI.** It guarantees no model calls, no cost surprises,
and no repair that nobody reviewed — a drifted script becomes a visible
failure that someone fixes deliberately, on a branch, in a diff.

```yaml
- run: atr run --behavior tests/*.test.txt --no-compile --headless
```

## Editing

Edit the **spec**, not the script — the next run recompiles from it. If you
edit the script by hand it keeps working, but its header no longer matches the
spec, so the following run will regenerate and overwrite your changes. To keep
a hand-written script, remove the `atr-spec-sha256` line; ATR will then treat
it as stale and refuse to run it under `--no-compile` rather than silently
replacing it.

## Limitations

- Compilation drives the real application, so the first run needs the app in a
  state where the spec can actually be completed.
- A repair is bounded to one attempt per run by default. A test that needs
  repeated repairs is telling you something that more repairs will obscure.
- `atr.fillSecret` needs a secret backend to be configured. Without one it
  fails loudly rather than filling an empty value.
